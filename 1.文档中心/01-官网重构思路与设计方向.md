# lord Li 个人官网重构：结构、设计方向与技术方案

日期：2026-11-13  
状态：讨论稿；视觉方向已选择「艺术展陈式」，尚未进入页面实现。

## 1. 核心建议

把官网建设为一个有鲜明作者气质的个人品牌空间：用艺术展陈式首页建立第一印象，用作品证明实践能力，用系统化文章体现专业积累，并为其他程序提供稳定的公共内容与素材。

**视觉关键词：大胆、鲜明、秩序、留白、精确。**

首页像进入一场关于 lord Li 的个人展览：有主视觉、有精选作品、有思想线索。文章内页像一本经过专业编排的书，适合认真阅读。两者共享字体、网格、色彩和导航体系。

建议采用 **Astro 静态生成 + TypeScript + Markdown 内容集合 + 结构化 JSON 素材 + Pagefind 全文搜索**。页面正文在构建时生成完整 HTML，动效按需增强。这个组合适合现有内容规模，也适合后续持续写文章、增加作品与公共素材。

“完美 SEO”在本项目中应落实为可验收的技术质量、迁移质量和内容质量；搜索排名与收录结果仍需上线后持续观察，不能靠技术方案保证。

## 3. 信息架构

### 3.1 六个主要栏目

| 栏目 | 英文名称 | 主要任务 | 页面形态 |
| --- | --- | --- | --- |
| 个人简介 | About | 让访客了解你的背景与能力 | 简介、经历、技能、教育认证、联系方式 |
| 个人作品 | Work | 展示实际做过的产品 | 作品总览，后续可增加作品详情 |

桌面导航建议：左侧 `lord Li` 字标，中央六个栏目，右侧搜索入口及 `中文 / EN`。英文标签较长，宽度不足时改为菜单，避免导航拥挤。移动端使用清晰的展开菜单，搜索与语言切换保持易于发现。

首页独立于六个栏目，点击字标返回首页。联系方式放在个人简介及页脚，不增加第七个主栏目。

### 3.2 首页叙事顺序

1. **开场：建立身份。** 大字号 `lord Li`、现有职业定位、简短介绍，提供「看作品」「了解我」两个入口。视觉文案暂用现有事实，不添加未经确认的成就。
2. **精选作品：展示实践。** 当前两件作品用不同尺度排列，像展品一样获得独立空间。
3. **个人简介摘要：建立信任。** 摘录现有背景、教育和认证，完整内容进入简介页。
4. **思想与方法：进入内容。** 产品理念、项目管理、编程各有简明导语及精选文章入口，展示真实文章标题。
5. **公用素材：展示开放内容。** 以乐理资源作为首个资源系列的候选入口。
6. **结尾与联系。** 简洁的联系邀请、邮箱、GitHub、微信入口，以及备案信息。

精选文章通过人工字段指定；没有可信日期时，不把旧文章包装成“最新发布”。

## 4. 视觉主方向：艺术展陈式个人品牌

用户已明确选择「更大胆、更鲜明，强调个人辨识度」。因此，后续视觉探索以艺术展陈式为主，不再把暖白编辑式当作默认方案。

### 4.1 想要营造的第一印象

访客进入网站时，先感受到明确的个人气质与设计判断，再逐步了解产品、管理和技术能力。

“高端”主要来自版式的控制力：字号比例大胆但有层级，作品尺度有变化但服从网格，色彩鲜明但使用集中，每个交互都具有清楚的反馈。

### 4.2 建议的视觉系统

| 维度 | 建议 |
| --- | --- |
| 基础色 | 纸白 `#F4F1EA` 与墨黑 `#181818`，形成展览图录般的基底 |
| 标识色 | 朱橙 `#F04A24`，用于章节、编号、局部大色块与重点交互 |
| 色彩比例 | 大面积中性色，标识色集中出现在关键位置；以视觉稿实际效果校准 |
| 字体表达 | 英文使用具有性格的展示字体，中文使用结构干净的黑体；正文优先可读性 |
| 标题尺度 | 桌面首屏字标约 120–200px，按屏幕宽度自适应；移动端允许换行 |
| 版式 | 桌面 12 列网格，非对称构图，大留白与局部满幅色块交替 |
| 细节 | 细线、章节编号、短标签、精确对齐，形成统一的展览识别体系 |
| 图片 | 优先使用真实头像、作品二维码与后续真实界面截图；缺图时用排版构图 |
| 圆角与阴影 | 以直角和轻微圆角为主，作品不依赖厚重阴影塑形 |

色号和字号是第一版视觉探索的起点，不是已经验证的设计定稿。朱橙色块上的小字优先使用墨黑；正文链接采用足够深的强调色，并实测对比度。正文普通文字对比度目标至少 4.5:1。

字体正式选型时确认授权与中文覆盖；控制字体文件体积，优先本地托管和合理子集化，避免字体加载拖慢首屏。

### 4.3 首屏的具体构想

首屏采用海报式构图：

- 上方是轻量导航，下方以超大 `lord` / `li` 字标形成视觉重心。
- 职业定位沿网格的一侧排列，保留现有 `Professional Product & Project Manager` 的事实内容。
- 一块朱橙色的几何色面承担视觉标识，与字标形成前后层次。
- 真实头像作为个人身份元素加入构图，尺寸与裁切服从原图质量，不强行放大低分辨率照片。
- 底部给出清楚的下一步入口，让访客可以直接看作品或了解背景。

该构图可通过 HTML / CSS / SVG 实现。第一版先把排版、比例和响应式做好，再判断是否需要更复杂的视觉媒介。

### 4.4 作品如何展示

当前作品主要是小程序二维码，仍然可以形成专业的展陈感：每件作品由名称、编号、可选简介及二维码构成，使用不同的展板尺寸与网格位置安排节奏。

- 首批只使用原作品页明确列出的两件作品：`Purine Query Tool` 和 `Choosing Boyfriend`，暂不根据文件夹中的其他二维码推断作品身份。
- 二维码是可操作的核心内容：保留白色底板、安静区和足够清晰度，不做扭曲、镂空、颜色反转或遮挡。
- 提供点击放大与保存图片入口，并说明使用微信扫码或保存后识别；不假定普通网页按钮可以直接唤起对应小程序。
- 每个作品的数据预留中英标题、简介、封面、二维码与排序。简介为空时自然收起该区域。
- 后续有截图时，加入真实产品界面；有完整案例内容时，再开启作品详情页，避免当前生成空内容详情页。

现有个人经历与技能数据先照搬；不擅自更新工作年限，也不添加客户、奖项、项目成果或使用量。

### 4.5 动效语言

| 场景 | 建议效果 | 目的 |
| --- | --- | --- |
| 首次进入首页 | 字标遮罩揭示、色面短距离展开 | 建立开场记忆点 |
| 滚动进入作品 | 展板轻微上移、图片局部揭示 | 引导注意力进入作品 |
| 桌面悬停 | 标题下划线、箭头位移、局部色彩变化 | 表明可点击与当前焦点 |
| 页面跳转 | 简短淡入淡出；条件合适时做连续过渡 | 保持浏览节奏 |
| 文章阅读 | 目录定位、阅读进度、代码复制反馈 | 提升长文使用体验 |
| 搜索和菜单 | 清晰的展开与关闭过渡 | 帮助理解界面状态 |

多数反馈控制在约 150–250ms；开场表达可用约 500–800ms，实际以预览体验调整。内容不应等待整段动画结束才可使用。

保留系统滚动与正常指针；移动端减少位移与层次效果。支持 `prefers-reduced-motion`，关闭动画或脚本后仍可阅读正文、使用基础导航。键盘聚焦获得与鼠标悬停同等清楚的状态。

### 4.6 文章页的设计

文章页延续展览的编号、色彩和标题系统，正文采用安静的图书式排版。

- 中文正文约 17–18px，行高约 1.75–1.9；英文正文按实际字体调整。
- 版心控制在约 720–800px，并分别检查中英文每行字数与阅读舒适度。
- 桌面目录放在侧边，移动端折叠为目录按钮。
- 标题层级、引用、表格、代码、注释和图片说明统一设计。
- 产品理念保留现有系列顺序，提供上一篇 / 下一篇；新文章通过元数据继续加入。
- 项目管理、编程通过主题、分类和关联文章形成阅读路径。

## 5. 公用素材：网页与程序共享一个内容来源

参考文件：`/Users/lord/Coding/PD05-视唱练耳听音准-小程序/LianEr-v1-miniapp/miniprogram/theory/articles.ts`。

该文件目前包含 7 篇乐理文章。它不是普通正文列表，还包含 `id`、标签、摘要、开场、分节正文、口诀、适用边界、音符示例、测验、训练标识及辅助函数。

### 5.1 推荐组织方式

同一份内容在构建时产生两个输出：

1. **给人阅读的页面**：标题、分节正文、示例说明与测验内容，支持站内搜索和独立链接。
2. **给程序使用的数据**：稳定 URL 的 JSON、资源索引，以及可单独访问的图片或音频。

首批候选集合命名为 `music-theory`。后续按实际需求增加其他集合，无需预先设计一个通用素材管理平台。

### 5.2 最小数据约定

- 用 `collection + id + locale` 定位一项内容；现有 `staff-landmarks` 等 ID 保持稳定。
- JSON 外层带 `schemaVersion`，内部内容保留现有文章字段及完整嵌套结构。
- `examples` 保留 `notes`、`spellings`、`label`、`caption`；保留可选 `chords`、完整 `quiz`、`training` 与 `trainingLabel`。
- `training` 是消费程序的业务标识，网页不能凭它直接假定存在可打开的训练 URL。
- 原文件中的 `Array.from` 等派生内容在构建时展开为数据；`exampleNotes` 属于展示辅助函数，留在应用代码中。
- 记录实际来源、语言、更新时间及必要的素材使用说明。网页、搜索索引和 JSON 从同一份内容生成。
- 图片与音频采用明确的 MIME 类型与缓存策略。带内容版本的素材可长缓存；可变资源索引使用较短缓存或重新验证。

### 5.3 与现有小程序的关系

第一阶段保持现有小程序代码和运行方式，官网先具备公共数据输出能力。以后接入时，建议优先在小程序构建阶段同步内容，以保留离线使用能力和可控的发布版本。

若未来选择运行时远程获取，再验证小程序请求合法域名、缓存、请求失败回退与旧版本兼容；浏览器跨域消费则按实际部署配置 CORS。第一版不为尚未存在的消费方式增加服务端接口。

资源数据的破坏性变更进入 `/data/v2/`；已有 `/data/v1/` 消费方继续使用原有契约。

## 6. 中英双语

双语必须覆盖导航、栏目、个人简介、作品信息、文章和公用素材的可见文本。**只翻译菜单不算完整双语网站。**

建议采用中文、英文独立 URL 和独立内容，通过稳定内容 ID 关联同一篇文章的不同语言版本。

- 每页设置与正文一致的 `html lang`。
- 存在真实译文时，语言切换直接进入对应页面，并保留阅读上下文。
- 尚无译文时，明确提示当前只有原文，并提供原文入口及目标语言栏目入口；不生成重复原文的假译文页面。
- 现有英文个人资料先保留，补中文版本；现有中文文章先保留，逐步补英文版本。
- 可先生成翻译草稿，但专业术语、案例、代码与乐理音名需要复核后发布。
- 不为双语重复图片和二维码；仅对标题、说明和替代文本做本地化。

框架可以先支持两种语言和翻译状态，但正式声称全站双语完成前，所有公开内容都应具备已审核的对应版本。译文缺失时不输出对应的 `hreflang` 页面关系。

Google 建议为语言版本提供明确的替代链接关系。实现时使用互相对应的 `hreflang`，每个实际语言页面设置自身 canonical，不把全部英文页面 canonical 到中文。[参考：Google 多语言页面指南](https://developers.google.com/search/docs/specialty/international/localized-versions)。

## 7. 全站搜索

推荐 Pagefind：在生成站点后建立全文索引，浏览器按需加载搜索资源，适合静态内容站。其官方方案支持按页面语言建立索引，中文分词需使用扩展构建。[参考：Pagefind 多语言搜索](https://pagefind.app/docs/multilingual/)。

### 搜索范围与体验

- 覆盖简介、作品名称与实际简介、31 篇现有文章，以及公用素材的可见正文。
- 公用素材的标题、说明、分节、口诀等可以被搜索；装饰编号、全站重复导航和底部文案不进入正文索引。
- 搜索入口常驻导航，桌面支持 `⌘K / Ctrl+K`，移动端提供明确按钮。
- 结果显示标题、栏目、语言及高亮摘要；可按六大栏目筛选。
- 默认搜索当前语言，提供切换搜索语言的控件，使两种语言的内容均可找到。第一版不额外实现自动跨语言翻译查询。
- 除快捷搜索面板外，提供独立搜索页，允许通过查询参数分享搜索词。
- 搜索页设为 `noindex`；全文页面仍使用正常链接供搜索引擎发现。
- 内容重新构建时同步重建索引，避免页面与搜索结果不同步。

验收应包括中文短词、连续中文短句、英文关键词、混排技术词、作品名、乐理术语、无结果提示和键盘操作。

## 8. SEO：从结构、迁移和内容同时做好

### 8.1 可抓取与页面基础

- 所有公开文章和简介在初始 HTML 中包含完整正文，链接使用真实 `href`。
- 每页具有明确的主标题、合理标题层级、独立 title 与真实摘要。
- 图片有有意义的替代文本和明确尺寸；代码、表格和引用使用合适语义。
- 生成 sitemap，只列正式、可索引、成功响应的 canonical 页面，排除搜索结果页和未发布译文。
- 配置 robots.txt、HTTPS、规范域名、尾斜杠规则和真实 404。
- 提供 Open Graph 等分享信息；文章封面缺失时可生成统一品牌分享图。

这些是提升搜索可理解性和页面质量的基础，具体实施遵循 [Google SEO 入门指南](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)。

### 8.2 内容身份与结构化数据

- 个人简介表达真实背景、技能、教育、认证和可验证的联系信息。
- 文章保留内容来源；例如当前产品理念介绍涉及腾讯课程，应准确区分个人原创、学习整理与来源内容。
- 已知的真实发布时间与修改时间才输出日期；迁移日期不冒充原始发布日期。
- 按页面实际内容添加 `Person`、`ProfilePage`、`Article` 或 `BlogPosting`、`BreadcrumbList` 等适用结构化数据。
- 作品页面按真实属性描述；没有评论、评分、售价等事实时不添加对应字段。
- 栏目页增加简短导语与清楚的文章路径，避免只有大量标题堆积。

结构化数据只表达页面中真实可见的信息，其存在不保证特殊搜索展示。

### 8.3 旧站迁移

这是上线前必须完成的工作：建立旧 URL → 新 URL 的逐条映射，而不是把旧页面统一跳回首页。

| 旧路径示例 | 新路径示例 |
| --- | --- |
| `/about/portfolio/` | `/en/work/`，按原英文内容确定对应语言 |
| `/about/skills/` | `/en/about/#skills` |
| `/about/contact/` | `/en/about/#contact` |
| `/product/0-introduction/` | `/zh/product-thinking/0-introduction/` |
| `/project/how-to-define-priority/` | `/zh/project-management/how-to-define-priority/` |
| `/code/python/how-to-setup-python3-in-Mac/` | `/zh/programming/how-to-setup-python3-in-Mac/` |

以上是映射示例，实施时以旧站实际 URL 和每篇正文语言生成完整清单。根路径 `/` 进入新版首页，首页保留简介摘要和明确的简介入口。

由实际托管平台返回服务器或边缘层的永久重定向（301 / 308），控制跳转链长度。旧文章有外部链接的标题锚点尽量保留；重命名锚点时另做兼容。Google 的迁移指引建议保留重定向至少一年，长期保留更便于旧链接继续使用。[参考：Google 网站迁移指南](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)。

迁移也应检查旧图片路径。若现有素材被外部程序直接引用，需要保持访问或提供兼容映射。

### 8.4 性能与上线观察

目标为真实访问数据第 75 百分位达到 LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1，分别关注加载、交互与布局稳定性。[参考：Web Vitals](https://web.dev/articles/vitals)。

执行重点：首屏关键图优先加载、非首屏图片延迟加载、控制字体体积、脚本按需加载、预留图片尺寸、动效优先使用 transform / opacity，并检查中国大陆与海外访问关键资源的稳定性。

上线前用实验室工具检查；上线后根据实际流量观察真实体验。Lighthouse 分数是诊断依据，不能代替收录状态与真实用户数据。上线后提交站点地图到 Google Search Console 与百度搜索资源平台，并观察抓取错误、旧链接跳转和搜索表现。

## 9. 技术基础框架

### 9.1 技术选择与取舍

| 部分 | 推荐 | 原因 |
| --- | --- | --- |
| 页面生成 | Astro 静态输出 | 文章多、动态业务少，便于输出完整 HTML |
| 数据约束 | TypeScript 与内容 Schema | 检查必填字段、语言关系、资源结构与稳定 ID |
| 普通文章 | Markdown 内容集合 | 延续现有写作方式，新增文章成本低 |
| 乐理等资源 | 结构化 JSON | 同时生成网页和供程序使用的数据 |
| 样式 | CSS 变量与组件样式 | 统一品牌色、字号、间距与响应式规则 |
| 动效 | 原生 CSS / 浏览器能力优先 | 第一版保持轻量，明确效果需要时再引入依赖 |
| 搜索 | Pagefind | 随静态站构建索引，支持中英文 |
| 发布 | 静态托管与 CDN | 可沿用或适配现有主域名环境，具体平台待确认 |

Astro 的内容集合可对内容进行组织和 Schema 校验，适合统一文章元数据。[参考：Astro Content Collections](https://docs.astro.build/en/guides/content-collections/)。

Next.js 也能实现这些功能，但当前没有必须引入服务端业务的需求，因此先选择结构更轻的内容站方案。动画丰富程度由设计与按需交互决定，不依赖采用大型应用框架。

### 9.2 目录草案

```text
1.文档中心/
src/
  components/                   导航、作品、文章、搜索等组件
  layouts/                      首页、栏目、文章布局
  pages/                        双语路由与数据输出路由
  content/
    profile/{zh,en}/            个人资料
    product-thinking/{zh,en}/   产品理念
    project-management/{zh,en}/ 项目管理
    programming/{zh,en}/        编程
    resources/music-theory/     乐理结构化内容
  data/                         作品信息、栏目定义、旧 URL 映射
  i18n/                         界面文案
  styles/                       品牌变量、排版、组件与动效
public/
  media/                        公共素材
```

`/data/v1/...` 的 JSON 从资源内容生成，不另存一份手工维护的数据。文档中心和内部检查文件均不进入最终公开产物。原备份和线上参考目录在正式内容迁移后已清理。

### 9.3 内容扩展方式

文章最小元数据包括：稳定 ID、语言、标题、摘要、分类、标签、slug、翻译关联 ID。日期、来源、封面、系列顺序、精选标记按真实情况填写。

新增文章时添加内容文件与必要元数据，自动进入相应栏目、搜索索引与站点地图。新增作品时添加一条作品记录及实际素材。已有 ID 和 URL 不因排序或标题变化而变化。

迁移旧 Markdown 时，处理图片相对路径、外部资源、MkDocs 特有语法、内嵌旧式 HTML、表格与代码块；保持正文含义和案例事实。

## 10. 实施顺序与验收

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| 1. 视觉定向 | 艺术展陈式首页、作品区、文章页视觉稿及移动端方向 | 个性、专业感、内容层级与阅读体验得到确认 |
| 2. 可运行框架 | 导航、双语路由、首页、六个栏目、作品列表、文章模板、资源模板 | 所有入口可用，桌面与手机布局成立 |
| 3. 内容迁移 | 现有个人内容、2 件作品、31 篇文章；确认后的首批资源 | 内容完整，来源准确，图片、代码、系列顺序正常 |
| 4. 搜索与双语 | 全文索引、语言切换、对应译文及翻译状态 | 中文与英文查询有效，语言切换行为明确 |
| 5. 发布准备 | SEO 元信息、重定向清单、公共数据输出、性能检查 | 无关键断链、错误语言关系或资源契约问题 |

框架阶段不能只提供首页视觉：至少需要打通首页 → 栏目 → 文章、首页 → 作品 → 二维码、资源目录 → 阅读页 → 数据文件，以及搜索和语言切换这几条路径。

正式上线的具体托管与域名切换另行安排；讨论与本地框架阶段不触碰当前稳定运行的官网。

## 11. 接下来优先讨论的设计问题

已经确定：主风格为艺术展陈式，强调大胆、鲜明与个人辨识度。

下一步建议先围绕一套具体方向评审：**纸白与墨黑为底、朱橙作为个人标识、超大字标、非对称作品展板、克制的动效、安静的文章正文。**

需要通过视觉稿判断的是：朱橙是否符合个人气质，首屏头像的存在感，字标的大胆程度，以及作品区的展陈密度。这些选择可以调整，不影响六大栏目、双语、搜索和公共素材的基础结构。
